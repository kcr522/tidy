# Tidy Constitution

> **TIDY** (타이디 / TidyUp): '정돈된, 깔끔한'이라는 뜻으로, 일상 관리를 깔끔하게 해준다는 메시지를 담았다.

Tidy 프로젝트의 모든 기획, 설계, 구현이 지켜야 하는 원칙이다. 스펙(spec.md), 계획(plan.md), 작업(tasks.md)은 이 원칙과 충돌하면 안 된다.

## Core Principles

### I. 하나의 코드로 네 가지 환경 (One Codebase, Four Targets)

Tidy는 **모바일 앱, 데스크톱 앱, 모바일 웹, 데스크톱 웹** 네 가지 환경에서 같은 기능으로 동작해야 한다.

- 화면과 기능 코드는 하나만 만든다. 환경별 코드는 "앱으로 감싸는 부분"(패키징)에만 둔다.
- 새 기능은 최소한 모바일 웹(폭 360px)과 데스크톱 웹(폭 1280px)에서 확인한 뒤 완료로 본다.
- 특정 환경에서만 되는 기능(예: 앱 전용 알림)은 1차 범위에 넣지 않는다.

### II. 서버 없이, 기기 안에서 (Local-First, No Server)

Tidy는 학교 서버나 외부 서버에 연결하지 않는다.

- 모든 데이터는 사용자의 기기 안 로컬 DB에 저장한다.
- 로그인, 회원가입, 원격 API 호출을 1차 범위에 넣지 않는다.
- 인터넷이 끊겨도 모든 기능이 동작해야 한다. 예외는 스크랩한 링크를 여는 것 하나뿐이다.
- 데이터를 잃지 않도록 JSON 내보내기/가져오기(백업)를 반드시 제공한다.

### III. MVP 먼저, 완벽하게 (MVP First, Done Right)

1차 목표는 기능 개수가 아니라 **핵심 기능이 빠짐없이, 버그 없이 동작하는 것**이다.

- spec.md에서 P1으로 표시한 기능이 모두 끝나기 전에는 P2 기능을 시작하지 않는다.
- 기능마다 입력 검사, 빈 화면 안내, 삭제 확인 같은 기본 예외 처리를 함께 만든다.
- 범위 밖으로 정한 기능(spec.md의 "1차 범위 밖")은 아이디어가 떠올라도 다음 버전으로 미룬다.

### IV. 단순하게 (Keep It Simple)

- 혼자 7일 안에 만들 수 있는 구조를 유지한다. 필요 없는 추상화, 상태 관리 라이브러리, 서버 코드를 넣지 않는다.
- 데이터 접근은 저장소(repository) 계층 하나를 거친다. 나중에 저장 방식을 바꿔도 화면 코드는 그대로 둘 수 있게 하기 위해서다.

### V. 매일 기록하기 (Commit Every Day)

- 하루 작업이 끝날 때마다 GitHub에 커밋하고 푸시한다.
- 커밋 메시지에는 무엇을 했는지 한국어로 짧게 적는다. 예: `feat: 가계부 입력 폼 구현`
- tasks.md의 체크박스를 실제 진행 상황과 맞춰 둔다.

## 기술 제약

- 언어와 화면: TypeScript + React (웹 기술 하나로 네 환경 모두 대응)
- 로컬 DB: 브라우저/앱 내장 IndexedDB (Dexie.js 사용)
- 앱 패키징: 모바일 앱은 Capacitor, 데스크톱 앱은 Tauri
- 화폐는 원(KRW), 언어는 한국어, 날짜는 기기의 현지 시간 기준

## 개발 흐름

1. 기능 아이디어 → `spec.md`에 요구사항으로 정리
2. `plan.md`에 기술 방식 정리
3. `tasks.md`의 작업을 위에서부터 하나씩 구현
4. 모바일 폭과 데스크톱 폭에서 직접 눌러 보고 확인
5. 커밋 & 푸시

## Governance

- 이 문서는 프로젝트의 다른 모든 문서보다 우선한다.
- 원칙을 바꿀 때는 이 문서를 먼저 고치고, 버전과 날짜를 올린다.
