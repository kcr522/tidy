## 1. 한눈에 보기

**Tidy**는 가계부 · 할 일 · 스크랩을 한 앱에 모은 개인용 생활 정리 앱입니다. 하나의 코드로 폰 앱, 컴퓨터 앱(PWA 설치), 폰 웹, 컴퓨터 웹 네 곳에서 돌아갑니다.

| 구분 | 지금 상태 |
|---|---|
| 1차 MVP (가계부 · 할 일 · 스크랩 · 대시보드 · 백업) | ✅ 완성 |
| 2차 (캘린더 · 일기 · 습관 · 적금 · AI 비서 · 캡처 입력 · 로그인과 동기화) | ✅ 완성 |
| 3차 (앱 잠금 · 위젯 · 반복 할 일 · 예산 · 자동 백업 · 월간 리포트 · 구글 캘린더) | ✅ 7가지 모두 완성 |
| 다듬기 (캘린더 개편, 스크랩 자동 캡처, 일기 자동 저장, 분할 화면 등) | ✅ 계속 진행 중 |
| 합친 PR | 78개 중 **77개 합침**, 1개 검토 중 (#68) |
| 실제 폰에서 아직 확인 못 한 것 | 지문 잠금, 백업 고친 것, 분할 화면, 음식 사진 기록 등 ([5-2](#5-2-만들었지만-실제-폰에서-아직-확인-못-한-것)) |
| 남은 일 · 정할 일 | 구글 캘린더 양방향 마무리, 플레이 스토어 방식 선택 ([5-3](#5-3-열려-있거나-막힌-일), [5-4](#5-4-정해야-하는-것)) |

- 학교 서버와 상관없이 **내가 실제로 쓰려고** 만드는 앱으로 시작했습니다. 처음에는 서버 없이 기기 안 DB에만 저장하는 것이 원칙이었습니다.

## 3. 기술 선택: 무엇을, 왜 썼나

### 3-1. 한 줄 요약

**웹 기술(TypeScript + React)로 한 번 만들고, 그 결과물을 웹사이트 · PWA · 폰 앱으로 감싸서 네 곳에서 쓴다.** 처음 조건이 "폰 앱, 컴퓨터 앱, 폰 웹, 컴퓨터 웹을 혼자서 7일 안에, 서버 없이"였기 때문에, 코드 한 벌로 네 곳을 해결하는 것이 가장 중요한 기준이었습니다. 처음 기술 검토는 [specs/001-tidy-mvp/research.md](../specs/001-tidy-mvp/research.md)에 있습니다.

### 3-2. 쓴 언어

| 언어 | 어디에 | 양 |
|---|---|---|
| **TypeScript** | 앱 화면과 기능 전부(`src/`), 서버 함수(`api/`), 시험 코드 | 파일 약 240개, 약 2만 7천 줄 |
| **Java** | 안드로이드 전용 기능 플러그인 6개 (지문, 구글 인증, 앱 업데이트, 홈 위젯, 공유받기, 스크랩 캡처) | `android/app/src/main/java/com/kcr522/tidy/` |
| **CSS (Tailwind)** | 화면 꾸미기 | `src/index.css` + 클래스 |
| **YAML** | 안드로이드 APK 자동 빌드 | `.github/workflows/android.yml` |

**왜 TypeScript인가**: 자바스크립트에 "자료 모양(타입)"을 붙인 언어입니다. 화면 · 서버 함수 · 시험을 한 언어로 쓸 수 있고, 잘못된 값을 넣으면 실행 전에 미리 알려 줘서 혼자 큰 앱을 고칠 때 실수를 줄여 줍니다. 그냥 자바스크립트는 배우기 쉽지만 앱이 커질수록 실수가 늦게 드러납니다.

**왜 Java도 조금 썼나**: 지문 인식, 홈 화면 위젯, APK 설치처럼 웹으로는 할 수 없는 안드로이드 기능만 Capacitor 플러그인으로 직접 만들었습니다. Kotlin도 가능했지만, Capacitor가 만들어 준 안드로이드 프로젝트가 Java라서 그대로 맞췄습니다.

### 3-4. 후보를 비교하고 고른 이유

#### 화면 프레임워크: React + Vite

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **React + Vite (고름)** | 결과물이 그대로 웹사이트라 네 곳을 한 코드로. 자료 · 예제가 가장 많음. Vite는 설정 없이 바로 시작, 고치면 화면이 즉시 바뀜 | 앱 느낌을 내려면 디자인을 직접 신경 써야 함. 웹뷰라서 아주 무거운 화면은 네이티브보다 조금 느림 |
| Flutter | 앱이 매끄럽고 예쁨. 한 코드로 앱 · 웹 · 데스크톱 | Dart 언어를 새로 배워야 함. 웹 버전 첫 로딩이 무거움(수 MB) |
| React Native + Expo | 진짜 네이티브 화면이라 앱 품질이 좋음 | 웹 · 컴퓨터 지원이 약하고, 웹 라이브러리를 그대로 못 씀. 설정이 복잡함 |
| Vue / Svelte | 배우기 쉽고 가벼움 | React보다 예제 · 라이브러리가 적음. 큰 차이는 없었음 |
| Next.js | 서버 화면 그리기, 검색 노출에 강함 | 서버 없이 기기에 저장하는 앱에는 필요 없는 기능이 많고 무거움 |

**결론**: "웹이 곧 앱"이 되는 길이 가장 짧았고, 자료가 많아서 막혔을 때 풀기 쉬웠습니다.

#### 폰 앱으로 만들기: Capacitor

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Capacitor (고름)** | 웹 결과물을 그대로 안드로이드 · 아이폰 앱으로 감쌈. 필요하면 Java 플러그인으로 네이티브 기능 추가 | 화면은 웹뷰라서 아주 화려한 애니메이션은 한계. 웹뷰 특유의 문제(CORS, HEIC, 캐시)를 따로 고쳐야 했음 |
| Cordova | Capacitor의 옛 형제, 플러그인이 많음 | 오래되고 관리가 줄어듦 |
| React Native / Flutter | 앱 품질이 가장 좋음 | 위와 같이 코드를 새로 짜야 함 |
| PWA만 | 설치 없이 홈 화면에 추가 | 지문, 홈 위젯, 공유받기, 정해진 시간 알림 같은 폰 기능이 약함 |

#### 컴퓨터 앱: PWA 설치

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **PWA 설치 (고름)** | 크롬 · 엣지 주소창의 "앱 설치" 한 번. 따로 설치할 도구 없음, 용량 거의 없음, 웹을 고치면 자동으로 최신 | .exe · .dmg 설치 파일이나 앱스토어 배포는 안 됨 |
| Tauri | 설치 파일이 작음(5~10MB) | Rust를 따로 설치해야 함 |
| Electron | 설치 파일 배포 가능, 널리 쓰임 | 크롬을 통째로 넣어 100MB 넘게 큼 |

필요해지면 같은 결과물을 Tauri나 Electron으로 감싸면 되므로, 지금은 가장 가벼운 길을 골랐습니다.

#### 저장: IndexedDB + Dexie

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **IndexedDB + Dexie (고름)** | 모든 브라우저와 앱 웹뷰에 기본으로 있어서 저장 코드 한 벌. 오프라인에서 바로 됨. Dexie의 `useLiveQuery`로 값이 바뀌면 화면이 저절로 바뀜 | 브라우저 데이터를 지우면 같이 지워짐 → JSON 백업과 자동 백업, 로그인 동기화로 보완 |
| localStorage | 가장 쉬움 | 5MB 정도로 작고 검색 · 정렬이 어려움 |
| SQLite (앱) + IndexedDB (웹) | 앱에서 더 튼튼함 | 저장 코드를 두 벌 만들어야 함 |

#### 로그인 · 동기화: Firebase

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Firebase (고름)** | 구글 로그인이 가장 쉬움. 무료 요금제로 10명 정도는 충분. 사람별로 데이터 나누는 규칙을 쉽게 씀 | 문서 하나 1MB 제한이 있어서 큰 첨부 파일(약 650KB 넘는 것)은 기기에만 남음 |
| Supabase | SQL(Postgres) 기반, 오픈소스 | 처음 요구는 "서버 없이"였고 기기 저장이 중심이라 SQL 서버의 장점이 작음. 무료 프로젝트는 한동안 안 쓰면 멈춤 |
| 직접 서버 만들기 | 마음대로 다 됨 | 서버 관리 · 보안 · 비용을 혼자 감당해야 함 |

처음에는 로그인 없이 기기에만 저장하는 원칙이었고, 11월 10일 "구글 로그인만, 10명 정도"로 정하면서 Firebase를 붙였습니다. 로그인 없이 쓰기도 그대로 남겨 두었습니다.

#### 웹 배포 · 서버 함수: Vercel

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Vercel (고름)** | 무료. GitHub에 올리면 자동 배포, PR마다 미리보기 주소. `api/` 폴더에 TypeScript 서버 함수를 바로 둘 수 있음(링크 미리보기, AI 키 숨기기, 구글 캘린더 등) | 무료 요금제는 함수 실행 시간 · 횟수에 한도 |
| GitHub Pages | 무료, 간단 | 서버 함수가 없어서 AI 키를 숨기거나 다른 사이트 내용을 읽을 수 없음 |
| Netlify | Vercel과 비슷 | 큰 차이 없음. Vite + 함수 조합은 Vercel이 더 단순했음 |

#### 화면 꾸미기: Tailwind CSS

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Tailwind (고름)** | 클래스 이름만으로 폰/컴퓨터 화면 나누기(`md:`, `short:`)가 쉬움. 디자인을 직접 정할 수 있어서 토스 같은 둥근 카드와 그라데이션을 자유롭게 | 클래스가 길어져 코드가 지저분해 보일 수 있음 |
| MUI · Chakra 같은 부품 모음 | 버튼 · 창을 바로 씀 | 다 비슷한 모양이라 원하는 디자인을 내기 어렵고 무거움 |
| 직접 CSS | 제한 없음 | 반응형과 다크 모드를 다 손으로 써야 해서 느림 |

차트도 라이브러리 없이 SVG로 직접 그려서 앱 크기를 작게 유지했습니다.

#### AI: 무료 Gemini → Groq → 기본 모드

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **Gemini 무료 (1순위)** | 무료로 사진도 읽음. 쓸 수 있는 모델을 구글에 물어보고 고름 | 하루 · 분당 한도가 있음 |
| **Groq 무료 (2순위)** | 빠르고 무료 | 한도 있음. 모델 이름이 자주 바뀜 → 자동으로 찾게 함(#71) |
| **기본(규칙) 모드 (3순위)** | 인터넷 · 키 없이 항상 됨. 21개 중 17개 맞음 | 자유로운 문장은 잘 못 알아들음 |
| Claude API | 정확도가 가장 좋음 | **유료**라서 쓰지 않기로 함 (#63에서 완전히 뺌) |
| 앱 안에 AI 모델 넣기 | 인터넷 없이 됨 | 앱이 수백 MB 커짐 → "앱 크기 안 키우기" 원칙과 맞지 않음 |

일정 · 지출 · 예산 같은 질문은 AI를 부르지 않고 내 기록에서 바로 답하게 해서(#64) 한도도 아꼈습니다.

#### 은행 캡처 글자 읽기: tesseract.js

| 후보 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **tesseract.js (고름)** | 무료, 기기 안에서 읽어서 은행 화면이 밖으로 나가지 않음 | 처음 쓸 때 글자 데이터를 받아야 하고, AI보다 덜 정확함 |
| 구글 Vision 같은 클라우드 OCR | 정확함 | 유료이고 은행 화면을 밖으로 보냄 |
| AI가 사진 읽기 | 가게 이름까지 알아서 정리 | 한도를 많이 씀 |

#### 시험 도구: Vitest + oxlint

Vite와 같은 설정을 그대로 쓰는 Vitest로 단위 시험을 돌리고(가짜 IndexedDB로 DB 시험까지), 코드 검사는 아주 빠른 oxlint를 씁니다. Jest · ESLint도 가능하지만 Vite 프로젝트에서는 설정이 더 많습니다.

## 이 문서 고치는 법

기능을 더하거나, 고치거나, 요구사항이 바뀔 때마다 같은 PR 안에서 이 문서를 함께 고칩니다.

1. **6. 변경 기록** 표 맨 아래에 한 줄을 더합니다: `| 날짜 | #PR | 종류 | 내용 | 상태 |`. PR 없이 정한 것은 PR 칸에 `—`, 종류에 `결정`.
2. **4. 기능 목록**에서 해당 영역 표에 줄을 더하거나 상태를 바꿉니다.
3. 폰에서 아직 확인 못 했으면 **5-2**에, 막혔거나 정할 게 있으면 **5-3 · 5-4**에 적고, 끝나면 지웁니다.
4. DB 버전을 올렸으면 **3-5. DB 버전 기록** 표에, 새 라이브러리 · 서비스를 쓰면 **3-3**(필요하면 **3-4** 비교)에 줄을 더합니다.
5. 맨 위 **마지막 갱신** 날짜와 PR 번호를 바꿉니다.
6. PDF는 `node scripts/doc-pdf.mjs`로 다시 만듭니다.
